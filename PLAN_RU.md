# План проекта: VPN-сервис с обфускацией трафика

**Статус:** черновик плана v1.0
**Дата:** 2026-08-26
**Фаза 0 (сейчас):** один VPS, без платёжной системы
**Фаза 1 (позже):** платежи, мульти-VPS с саморегистрацией нод

---

## 1. Цель и концепция

VPN-сервис, чей главный принцип — **трафик должен быть неотличим от обычного HTTPS-трафика**, а сам факт использования VPN не должен определяться ни DPI-системами, ни активными пробами. Эталон по духу — Amnezia (AmneziaWG, XRay+Reality), но с упором на **менее очевидную маскировку**:

- никаких характерных handshake-паттернов,
- никаких открытых «подозрительных» портов,
- сервер выглядит как обычный веб-сайт,
- фолбэк: при заходе на сервер обычным браузером отдаётся настоящий контент (маскирующий сайт), а не таймаут и не пустой ответ.

### 1.1. Принципы дизайна

1. **Протокол не должен опознаваться.** Не OpenVPN, не классический WireGuard «как есть», не Shadowsocks в чистом виде (всё это fingerprintable).
2. **Активное зондирование = отдача маскировочного сайта.** Кто бы ни постучал — цензор, сканер, бот — получает реальный TLS-ответ от реального сайта.
3. **Бэкенд и панель не открыты наружу.** Управление — только через узкое окно (admin API за отдельным защищённым входом или через SSH-туннель на этапе MVP).
4. **Пользователь не управляет конфигами вручную.** Клиентское приложение / ссылка-подписка делает всё сама.
5. **Один бинарник-агент на ноде.** Нода устанавливается одной командой и сама подключается к панели (это фундамент для фазы «VPS добавляют себя сами»).

## 2. Выбор протоколов (ядро маскировки)

### 2.1. Основной стек — XRay-core + VLESS + XTLS Vision + REALITY

Это текущий «золотой стандарт» маскировки под TLS:

- **VLESS** — лёгкий протокол без собственной криптографической сигнатуры (в отличие от VMess/Trojan).
- **XTLS Vision** — потоковое шифрование без характерного «двойного TLS», убирает fingerprintable паттерны, которые выдавал старый XTLS.
- **REALITY** — ключевая фишка: сервер **не выпрашивает и не держит сертификат вообще**. TLS-хендшейк выполняется «от имени» реального стороннего сайта (dest-таргет, например `www.microsoft.com`, `dl.google.com`, `github.io`). Для DPI это **настоящий TLS с настоящим сайтом** — fingerprint идентичен легитимному, активная проба отвечает как реальный сайт, сертификат настоящий.
- Порт: **443 TCP** (стандартный HTTPS). Никаких экзотических портов.

**Почему это «менее очевидно, чем Amnezia по умолчанию»:**
- REALITY отбивает активные пробы на уровне «это настоящий сайт», а не «это подозрительный TLS-обрыв».
- Статистический анализ (размеры пакетов, тайминги) дополнительно маскируется XTLS Vision flow.
- Никаких доменов, привязанных к нашему VPS: сертификат чужой, легитимный.

### 2.2. Резервный транспорт — Shadowsocks-2022 / ShadowTLS v3

Для случаев, когда 443/TCP зарезан или DPI играет в «whitelisting by SNI»:

- **ShadowTLS v3** — TLS-туннель, где SS-трафик вложен в настоящий TLS-сессию к реальному сайту (handoff-фолбэк: если это не наш клиент — трафик честно проксируется на маскировочный сайт).
- Порт тоже 443 (multiplex через fallbacks или sni-маршрутизацию в XRay) или 8443.

### 2.3. «Грубая сила» — AmneziaWG (опционально, 3-й профиль)

AmneziaWG (обфусцированный WireGuard: рандомизация заголовков, junk-пакеты, изменённые magic numbers) — как **опциональный профиль** для пользователей, которым важна скорость UDP (игры, стриминг), а не максимальная скрытность. Помечаем в UI как «быстрый, менее скрытный».

### 2.4. Что исключаем

| Протокол | Почему нет |
|---|---|
| OpenVPN | детектится DPI по хендшейку, медленный |
| Классический WireGuard | характерный UDP-fingerprint, легко блокируется |
| Trojan/TLS «классика» | fingerprintable active-probing поведение, нужен свой сертификат/домен |
| Hysteria/TUIC | QUIC-based, легко опознаётся как VPN-туннель, блокируется по QoS/UDP-фильтрам (можно добавить позже как опцию) |

### 2.5. Маскирующий сайт (decoy)

На каждой ноде — контейнер `decoy-site`: статический сайт (Nginx/Caddy), отдающий правдоподобный контент (корпоративный лендинг / блог / «under construction»). REALITY + fallback-маршрутизация: всё, что не прошло аутентификацию протокола, уходит на decoy. Сканер видит живой сайт.

## 3. Архитектура системы

### 3.1. Компоненты (один VPS, Фаза 0)

```
┌────────────────────────────────────────────── VPS-1 ──┐
│                                                        │
│  [ingress]                                             │
│   Caddy/Nginx (443 → маршрутизация панели и decoy)     │
│                                                        │
│  [vpn-core]                                            │
│   XRay (VLESS+Vision+REALITY :443)                     │
│   ShadowTLS (опц. :8443)                               │
│   AmneziaWG (опц. UDP :51820)                          │
│   decoy-site (Nginx, статика)                          │
│                                                        │
│  [panel-backend]                                       │
│   Admin API (Java / Spring Boot)                       │
│   PostgreSQL 16                                        │
│   Redis (сессии, rate-limit, кэш конфигов)             │
│                                                        │
│  [panel-frontend]                                      │
│   Admin UI (React)  — только для админа                │
│   User UI   (React)  — кабинет пользователя + подписка │
│                                                        │
│  [observability]                                       │
│   Prometheus + node_exporter + xray-exporter           │
│   Grafana                                              │
│   Loki + Promtail (логи, без payload!)                 │
│                                                        │
└────────────────────────────────────────────────────────┘
```

### 3.2. Важное архитектурное решение: разделение «control plane / data plane»

- **Control plane** = Admin API + БД + фронты. Живёт в своих контейнерах, наружу смотрит только через защищённый путь (например, `/panel` на отдельном поддомене с mTLS или IP-allowlist).
- **Data plane** = XRay/ShadowTLS/AWG. Не ходит в БД напрямую. Получает конфиг от Admin API через локальный Unix-сокет / localhost gRPC (XRay API) или по файлу конфига + hot-reload.
- Это разделение критично для Фазы 1: новые VPS будут поднимать **только data-plane + агента**, а control plane останется на первом сервере.

### 3.3. Сетевая схема портов (Фаза 0)

| Порт | Кто | Назначение |
|---|---|---|
| 443/tcp | XRay (REALITY) + Caddy | VPN-трафик + панель/подписка по SNI-маршрутизации |
| 8443/tcp | ShadowTLS | резервный транспорт (опц.) |
| 51820/udp | AmneziaWG | быстрый профиль (опц.) |
| 22/tcp | SSH | только с ключом, ограничение по IP админа (fail2ban) |
| — | Prometheus/Grafana | только localhost, доступ через SSH-туннель |

## 4. Backend — детально

### 4.1. Стек

- **Язык: Java 21 LTS (Spring Boot 3.x)** — выбор заказчика. Зрелая экосистема, из коробки: Spring Security, Spring Data, Actuator (метрики/health), gRPC-клиенты. Виртуальные потоки (Project Loom, `spring.threads.virtual.enabled=true`) дают высокую конкурентность без реактивного стека.
- **Фреймворк:** Spring Boot Web (REST), **grpc-java** для внутреннего протокола нода↔панель (Фаза 1) и для клиента XRay API. OpenAPI-контракт генерируется через `springdoc-openapi` (или contract-first через OpenAPI Generator).
- **БД:** PostgreSQL 16 + миграции **Flyway**. Доступ к данным — Spring Data JPA (Hibernate) или **jOOQ** для типобезопасного SQL там, где JPA мешает.
- **Кэш/очередь:** Redis — сессии, одноразовые токены подписки, rate-limit (Bucket4j + Redis), pub/sub для обновления конфигов нод (Spring Data Redis).
- **XRay-интеграция:** официальный **Xray gRPC API (HandlerService/StatsService)** — у XRay есть `.proto`-файлы, из них grpc-java генерирует клиента; добавление/удаление пользователей без перезапуска ядра. **Сам XRay остаётся отдельным контейнером (Go-бинарь)** — мы его не переписываем, а оркеструем.
- **Аутентификация:** JWT (access 15 мин + refresh 7 дней, jjwt или Spring Authorization Server), пароли — `argon2id` (Bouncy Castle / spring-security-crypto Argon2). Для админки обязательная 2FA (TOTP, библиотека `java-totp` / самописный RFC 6238).
- **Аудит-лог** всех действий админа (AOP-перехватчик или события Spring).

#### 4.1.1. Два разных артефакта: панель и агент

| | **panel** (control plane) | **node-agent** (Фаза 1, на каждом VPS) |
|---|---|---|
| Рантайм | JVM, Spring Boot 3, JDK 21 | Тот же Java-код, но собранный в **GraalVM Native Image** (или Quarkus Native) |
| Память | 512–768 МБ (норм для сервера панели) | 40–80 МБ в native-режиме — критично на дешёвых VPS |
| Старт | ~3–5 сек | ~50 мс |

Таким образом кодовая база одна (модуль `common`), но панель живёт как обычное Spring-приложение, а агент — как маленький нативный бинарник. Если GraalVM покажется сложным на старте — Фаза 0 вообще без агента, а к Фазе 1 либо осваиваем GraalVM, либо агент живёт на обычной JVM с `-Xmx128m` (тоже жизнеспособно на VPS от 2 ГБ).

#### 4.1.2. Альтернатива, если захочется «полегче»

**Kotlin + Ktor** или **Quarkus** — тот же JVM-стек, меньше бойлерплейта, нативная сборка проще. Но Spring Boot даёт максимум готовых батареек (security, data, actuator, testcontainers) и самую низкую кривую поиска разработчиков — берём его как основной вариант.

### 4.2. Модули бэкенда

```
backend/                       # Gradle multi-module проект (Kotlin DSL)
├── build.gradle.kts
├── settings.gradle.kts
├── common/                    # DTO, proto, utils — общий код панели и агента
│   └── src/main/proto/        # xray-api.proto, node-sync.proto (генерация grpc-java)
├── panel/                     # Spring Boot приложение (control plane)
│   └── src/main/java/com/vpn/panel/
│       ├── auth/              # JWT, TOTP, argon2id (Spring Security)
│       ├── users/             # CRUD пользователей, статусы
│       ├── devices/           # привязка устройств (UUID -> peer)
│       ├── subscription/      # генерация subscription-ссылок (VLESS/SS/AWG)
│       ├── configgen/         # генерация конфигов XRay/AWG из шаблонов (Freemarker/Pebble)
│       ├── xrayctl/           # gRPC-клиент XRay API (add/remove user, stats)
│       ├── nodes/             # (Фаза 1) реестр VPS-нод, токены регистрации
│       ├── billing/           # (Фаза 1) заглушка под платёжный модуль
│       ├── audit/             # аудит-лог (Spring AOP / ApplicationEvents)
│       └── metrics/           # Micrometer -> Prometheus
├── agent/                     # (Фаза 1) node-agent, сборка GraalVM native

```

### 4.3. Модель данных (минимум)

- `users(id, email, password_hash, role[admin|user], status, totp_secret, created_at)`
- `devices(id, user_id, name, uuid, public_key, protocol, created_at, revoked_at)`
- `subscriptions(id, user_id, token_hash, expires_at, traffic_limit_bytes)`
- `traffic_stats(device_id, node_id, ts, uplink, downlink)` — агрегированные, без содержимого трафика!
- `nodes(id, hostname, ip, status, token_hash, last_seen_at)` — Фаза 1, но таблицу и API закладываем сразу
- `audit_log(actor_id, action, payload, ts)`

### 4.4. API (черновик контракта)

**Админ:**
```
POST   /api/v1/auth/login          (TOTP step)
POST   /api/v1/users               CRUD пользователей
POST   /api/v1/users/:id/devices   выдать конфиг/ссылку
GET    /api/v1/stats/overview      трафик, онлайн, топы
GET    /api/v1/nodes               (Фаза 1: список нод)
POST   /api/v1/nodes/enroll-token  (Фаза 1: токен для саморегистрации VPS)
```

**Пользователь:**
```
POST   /api/v1/auth/login
GET    /api/v1/me                  статус, трафик, срок
GET    /api/v1/me/devices          список своих конфигов
POST   /api/v1/me/devices          добавить устройство (лимит N)
GET    /sub/:token                 subscription-ссылка (VLESS URI / sing-box JSON / AWG conf)
```

### 4.5. Приватность by design

- Логи XRay — уровень `warning`, **без access-log с доменами**. Мы храним только счётчики байт для лимитов.
- Нет логирования содержимого трафика нигде, ни на каком уровне.
- Отдельная политика ротации и хранения логов (7 дней максимум для технических логов).

### 5.3. User UI (кабинет пользователя)

Максимально простой:

3. **Мои устройства** — список, удаление, переименование.
4. (Фаза 1) **Оплата** — тариф, продление, история платежей.

### 5.4. Subscription-эндпоинт

`GET /sub/:token` с User-Agent-роутингом: sing-box-клиентам отдаём JSON, v2rayNG — base64-список URI, браузеру — HTML-страницу с инструкцией. Токен — длинный случайный, хэш в БД, возможность отзыва.

## 6. Docker и оркестрация

### 6.1. Фаза 0 — Docker Compose на одном VPS

Kubernetes на одном VPS — избыточен, но пользователь хочет K8s → решение: **Compose сейчас, манифесты K8s пишем сразу и держим в репо** (Helm-чарт), чтобы переход на кластер был безболезненным. Либо сразу **k3s** на одном VPS — легковесный K8s, даёт настоящий Kubernetes API с минимальными накладными (~512 МБ RAM).

**Рекомендация:** `k3s` сразу — одна команда установки, Helm-чарты работают, путь к мульти-нодовой Фазе 1 нативный (агент ноды = DaemonSet).

#### docker-compose.yml (сервисы)

```yaml
services:
  caddy:        # ingress: 443 -> decoy / panel / sub
  xray:         # VLESS+REALITY, конфиг из /etc/xray (mounted), API на 127.0.0.1:10085
  shadowtls:    # опционально, profile: extra
  amneziawg:    # опционально, profile: extra (или awg через xray)
  decoy-site:   # nginx + статика маскировочного сайта
  backend:      # Spring Boot API (eclipse-temurin:21-jre / jlink-образ)
  postgres:     # 16-alpine, volume pgdata
  redis:        # 7-alpine
  admin-ui:     # статика React
  user-ui:      # статика React
  prometheus/grafana/loki/promtail:  # observability-стек, профиль monitor
```

- Все образы — multi-stage сборка, финальные `distroless`/`alpine`, без root внутри (`USER 10001`), read-only FS где возможно.
- Секреты — через `.env` + Docker secrets, **не в git**.
- Healthchecks у всех сервисов, `restart: unless-stopped`.
- Отдельные внутренние сети: `net-data` (xray↔decoy↔caddy), `net-ctrl` (backend↔db↔redis↔xray-api-localhost).

### 6.2. Helm-чарт (сразу, для k3s и будущего кластера)

```
deploy/helm/vpn/
├── templates/
│   ├── deployment-backend.yaml
│   ├── deployment-xray.yaml      # -> DaemonSet в Фазе 1
│   ├── statefulset-postgres.yaml
│   ├── ingress.yaml
│   ├── secrets.yaml              # sealed-secrets / external-secrets
│   └── monitoring/               # ServiceMonitor для Prometheus

```

### 6.3. CI/CD

GitHub Actions (или GitLab CI):
1. `lint + test` (Gradle test + JUnit/Testcontainers, tsc, eslint)
2. `build` образов, тег по git-sha, пуш в GHCR (приватный registry)
3. `deploy` — SSH на VPS, `docker compose pull && up -d` (Фаза 0) / `helm upgrade` (Фаза 1)
4. Автоматические миграции БД при деплое (job/initContainer)

- Ежедневный `pg_dump` → зашифрованный (age/gpg) архив → S3-совместимое хранилище или второй сервер. CronJob/контейнер `backup`.
- Конфиги XRay/ключи REALITY — в зашифрованном секрет-хранилище (SOPS + age в git).

## 7. Фаза 1 — мульти-VPS с саморегистрацией (закладываем сейчас)

Ключевая идея: **однострочная команда установки**, которую админ копирует из панели:

```bash
curl -sSL https://panel.example.com/install.sh | bash -s -- \
  --token <enroll-token> --panel https://panel.example.com
```

Что происходит на новом VPS:
1.  Ставится Docker (или k3s-agent).
2. Поднимается контейнер **node-agent** (модуль `agent` той же кодовой базы, собранный GraalVM native, ~50–80 МБ RAM).
3. Агент по enroll-token регистрируется в панели (POST /api/v1/nodes/enroll), получает: постоянный node-token (mTLS-клиентский сертификат), конфиг XRay, список пользователей (синхронизация через gRPC-stream).
4. Агент сам поднимает data-plane контейнеры (xray, decoy, exporters).
5. Панель видит ноду онлайн, начинает собирать её метрики и раздавать на неё пользователей.

Технические решения, которые надо заложить в Фазе 0, чтобы Фаза 1 не требовала переписывания:
- backend сразу проектируется с gRPC-интерфейсом для агентов (даже если пока никто не подключается);
- пользователи XRay управляются через API, а не правкой файла;
- конфиг XRay генерируется шаблонизатором (`configgen`) с параметрами ноды;
- decoy-сайт и набор dest-таргетов REALITY — пер-нодные настройки в БД.

## 8. Фаза 2 — платёжная система (позже, но закладываем интерфейсы)

- Абстракция `BillingProvider` в backend: `CreateInvoice(user, plan)`, webhook-обработчик, `OnPaymentConfirmed -> продлить подписку`.
- Провайдеры под будущее: Stripe, CryptoBot/CryptoPay (Telegram), ЮKassa — за интерфейсом.
- Тарифы как таблица `plans(id, name, traffic_limit, duration, price)` — админка управляет тарифами без деплоя.
- Промокоды/реферальные ссылки — опционально.

## 9. Безопасность (чек-лист)

- [ ] SSH: только ключи, fail2ban, нестандартный порт опционально
- [ ] UFW/nftables: наружу только 443 (+8443/51820 если включены профили)
- [ ] Панель — на отдельном поддомене/пути + IP-allowlist + 2FA
- [ ] Все контейнеры non-root, read-only FS, capability drop ALL
- [ ] Секреты в SOPS/sealed-secrets, никогда в git открыто
- [ ] TLS для панели — настоящий сертификат (Let's Encrypt)
- [ ] Ротация short-id / UUID по расписанию (опц.)
- [ ] Обновления образов еженедельно (Watchtower или Renovate + CI)
- [ ] Аудит действий админа
- [ ] Минимизация логов, без содержимого трафика
- [ ] Резервное копирование БД, проверка восстановления раз в месяц

## 11. Риски и открытые вопросы

1. **Выбор dest-таргета REALITY** — нужен популярный домен с TLS 1.3 + X25519, желательно из той же сети/региона, что и VPS, с поддержкой HTTP/2. Кандидаты проверяются скриптом; плохой таргет = плохая маскировка.
2. **Блокировка по поведенческому анализу** (объёмы/тайминги) — полностью не решается протоколами; mitigations: padding в XRay, лимиты сессий, mux.
3. **Память на маленьком VPS** (1–2 ГБ RAM): k3s + JVM-панель + Postgres + XRay могут не влезть в 1 ГБ. Митигация: панель с тюнингом heap (`-Xmx384m`, контейнерные лимиты, JVM видит cgroup-лимиты автоматически с JDK 17+), при 1 ГБ — чистый Compose без k3s и без observability-стека. Минимально комфортная конфигурация для полного стека — 2 ГБ.
4. **Юридика** — юрисдикция VPS-провайдера, ToS провайдера, налоги при подключении платежей (Фаза 2).
5. **Один VPS = единая точка отказа** — принимаем осознанно до Фазы 1; бэкапы конфигов позволяют поднять ноду заново за ~10 минут.
